# Setup

Machine configuration that makes the standing agent rules — the knowledge base and the response preferences — load automatically in every session, in Cursor, Claude Code, and Codex alike. Tracked here because it lives *outside* the repo when installed, so it would otherwise be lost on a new machine.

## The standing rules

Three bodies in this directory are the one source for the instructions that load into every agent session:

| Body | What it does |
|---|---|
| `knowledge-base.md` | Routes knowledge questions to `kb/INDEX.md`, enforces the three-file read budget, optionally tells the agent to read your repo's notes before its first git, build, or test command there, and draws the line between `kb/` and `personal/`. |
| `response-preferences.md` | How replies are written: answer first and briefly, disagree plainly, make routine calls without asking, prefer a diagram where structure is the point, and ask before writing to shared systems. A general default meant to be edited. |
| `engineering-principles.md` | Five standing rules for how work gets done rather than how it is reported: prove it against the real artifact, build the lever, encode a repeated correction in structure, minimize reader load, sequence the work so it proves itself. Carries concrete verification traps inline — targeted tests, conflict resolutions, downstream green jobs, shared checkouts — because those recur often enough that pull-based `kb/lessons/` notes were not reaching the agent in time. Adapted from the `pstack` principle set, reduced to what survives without its tooling. |

Bodies write `{{KB_ROOT}}` wherever they mean this repo. The installer renders that to the clone's absolute path in `setup/.generated/` (git-ignored, because it holds your machine's paths), so the same text works from any working directory and any clone location. Edit the `.md` bodies here, never anything in `.generated/`, then re-run the installer.

Three agents read them, each through the mechanism that loads in every session regardless of what is open:

| Agent | Mechanism | Installed where |
|---|---|---|
| Cursor | One project rule per body, `alwaysApply: true` | `<parent of this repo>/.cursor/rules/<rule>.mdc`, generated as front matter + the rendered body; override with `CURSOR_RULES_DIR` |
| Claude Code | User-level `CLAUDE.md`, loaded for every project, importing each rendered body with an `@<repo>/setup/.generated/<rule>.md` line | `~/.claude/CLAUDE.md` |
| Codex | Global `AGENTS.md`, read before any repo-level `AGENTS.md` | `~/.codex/AGENTS.md`, generated by concatenating the bodies |

Adding a rule means dropping a body in this directory and adding one line to the `RULES` array in `install.sh`; the three install paths follow from that.

### Install, and re-install after editing

```sh
bash setup/install.sh          # write all three
bash setup/install.sh --check  # verify without writing; non-zero if anything drifted
```

The script renders each body and its `.mdc` into `setup/.generated/`, copies the `.mdc` to the Cursor rules directory (`CURSOR_RULES_DIR` overrides the default), renders `hooks.json` for you to merge, appends any missing import line to `~/.claude/CLAUDE.md`, and writes `~/.codex/AGENTS.md`.

`~/.codex/AGENTS.md` is a generated regular file carrying every body, separated by horizontal rules and led by an HTML comment marking it generated. The installer replaces a symlink or a file it previously generated, and refuses to overwrite a regular `AGENTS.md` that lacks that marker — merge that one by hand.

Claude Code notes: user-scope imports load without the approval prompt that project-level external imports get, and imports resolve up to four hops deep, so a body could itself import more files if it ever needs to. A `~/.claude/rules/` directory is the alternative for path-scoped rules (`paths:` front matter), which these rules do not need since the bodies already say when to apply.

Running the installer from inside Claude Code's own sandbox will fail on `~/.claude/CLAUDE.md`, `~/.codex/`, and the Cursor rules directory, all of which are outside the writable set; run it from a terminal.

### Why the workspace root and not this repo, for Cursor

Cursor loads `AGENTS.md` from subdirectories only when the agent is already working with files in that directory. Since this repo sits one level below the workspace root, its `AGENTS.md` won't fire on a cold question like "what do I know about X?" — nothing has touched the directory yet. A rule with `alwaysApply: true` at the workspace root has no such condition.

## Pre-commit hook

`.githooks/pre-commit` runs `scripts/kb.py check` and refuses commits that would leave the knowledge base inconsistent — missing front matter, an unroutable lesson, a broken link, a stale generated block. Hooks aren't installed by cloning, so enable it once per machine:

```sh
git config core.hooksPath .githooks
```

Bypass with `git commit --no-verify` when committing something genuinely unrelated.

## Hooks

`hooks/` holds two scripts.

`capture-check.py` nudges when a turn did substantive work and recorded nothing; it is Cursor-only, because it depends on a `stop` hook whose `followup_message` Cursor submits as the next user message.

`kb-autosync.py` runs `kb.py sync` at most once every twelve hours and is agent-agnostic. It exists because aging markers (`half_life`) live in generated blocks and therefore only move when `sync` runs, which nobody remembers to do. `install.sh` wires it to Claude Code's `SessionStart` (merging into `~/.claude/settings.json`, keeping a `.bak`, and skipping if already present), and it is listed on Cursor's `stop` array in `hooks.json`. Codex has no hook mechanism to wire it to, so under Codex the markers refresh on the next Claude or Cursor session.

It fails open and prints nothing unless a block actually changed. Its last-run stamp is `~/.cache/kb-sync/last-run`; override with `KB_SYNC_STAMP`. Because it runs `sync`, it can leave the repo with modified generated blocks — that is the intended outcome, and `check` will not fail on them.

### Install

Hooks merge across levels, so check what you already have before overwriting anything:

```sh
cat ~/.cursor/hooks.json          # existing user-level hooks, if any
cp setup/.generated/hooks.json ~/.cursor/hooks.json   # only if there's nothing to merge with; rendered by install.sh
```

If `~/.cursor/hooks.json` already exists, merge the two `hooks` objects by hand rather than replacing the file. Restart Cursor afterward.

### The removed `personal/` block

A `beforeReadFile` hook with `failClosed: true`, paired with a `beforeShellExecution` hook, used to deny agent access to `personal/`. Both were removed deliberately — `personal/` is an export boundary rather than a vault, and blocking reads mainly stopped the agent helping with the career notes and side projects kept there. Full reasoning in `personal/README.md`.

Two things it taught are worth keeping, because both generalize past this repo.

**A `failClosed` hook whose script lives in the repo it guards is a teardown hazard.** Deleting the script before unwiring it denies *everything*, including the edits needed to unwire it, because `failClosed` cannot tell "malicious" from "missing." Unwire first, delete second. This was learned the direct way.

**A permission rule the enforcement mechanism cannot see is not a rule.** The instruction carved out an exception for "unless the user names a file explicitly," but the hook received a file path and never the conversation, so consent had no route to reach it. An exception that cannot be expressed to the thing doing the enforcing will never once apply.

## Capture check

`hooks/capture-check.py` closes part of the gap left by capture triggers being *instructions* an agent may simply not act on. It watches what a turn actually touched, and if the turn did substantive work while writing nothing under `kb/`, it returns a `followup_message` from the `stop` hook — which Cursor submits as the next user message. A fresh user turn is a considerably stronger prompt than a rule loaded at session start.

It's wired to three events, all fail-open:

| Event | Role |
|---|---|
| `afterFileEdit` | Counts edits: under `kb/` means captured, outside the repo means work, elsewhere in the repo is system maintenance and ignored |
| `postToolUse` | Counts `Read`/`Grep`/`Glob` calls, so a read-only research session still registers |
| `stop` | Renders the verdict, then deletes the turn's state |

Installed by the `cp` above. State lives in `~/.cursor/kb-capture/` and self-prunes after 14 days; override with `KB_CAPTURE_STATE`.

### Deliberate limits

**It nudges at most once per conversation.** `loop_count` suppresses repeats and `loop_limit: 1` caps it a second way. An automation that nags gets uninstalled, which costs more than the notes it would have caught.

**`postToolUse` fires on every tool call.** Measured at ~35 ms per invocation on this machine, so a 200-call session pays a few seconds in aggregate. Drop that one event from `hooks.json` if it's noticeable; you lose detection of read-only sessions, which are the ones most likely to have established something worth recording.

**It cannot judge whether anything durable came up** — only the model can. So the follow-up states outright that "nothing to record" is a valid answer. Without that escape hatch the nudge becomes pressure to invent a note, and a fabricated note is worse than a missing one because it dilutes the real ones.

**Research detection is a heuristic**, tripping at 12 read/search calls. It will occasionally fire on a session that was just looking for a file.

### Verifying it

Feed it a synthetic turn rather than waiting to catch one:

```sh
export KB_CAPTURE_STATE=$(mktemp -d)
echo '{"hook_event_name":"afterFileEdit","conversation_id":"t","workspace_roots":["'"$(dirname "$PWD")"'"],"file_path":"/tmp/x.py"}' \
  | python3 setup/hooks/capture-check.py
echo '{"hook_event_name":"stop","conversation_id":"t","workspace_roots":["'"$(dirname "$PWD")"'"],"status":"completed","loop_count":0}' \
  | python3 setup/hooks/capture-check.py
```

The second command should print a `followup_message`. Every other path — captured, aborted, `loop_count` above zero, a workspace not containing this repo, malformed input — prints `{}`.
